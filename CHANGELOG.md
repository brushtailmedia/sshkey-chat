### Security
- **Signed room member attestation — store-and-forward (client crypto audit F7, server half, 2026-05-31).** Closes the room "shadow reader" gap: a malicious server could list itself/a colluder in `epoch_trigger`, making a legitimate member wrap the room epoch key for a hidden reader, with nothing verifying it (the pre-existing `member_hash` was unsigned, unimplemented, and — being relay-forwarded — forgeable per-victim). The rotating client now **signs** `(room, epoch, member_hash)`; the server's role is opaque **store-and-forward**: `handleEpochRotate` persists `(generator, member_hash, member_sig)` per `(room, epoch)` **atomically with the key batch** (extended `StoreEpochKeysBatch` + new `epoch_attestations` table + `GetEpochAttestation`) and forwards all three unchanged on every current-epoch `epoch_key` (live distribution, on-connect `sendEpochKeys`, `state_fix`). Sync/history (`SyncEpochKey`) deliberately do **not** carry it — those keys are skip-verified historical (client-side sync-path guard). The server performs no verification (it has no crypto); the cross-client verify + fail-closed is the sshkey-term half. Protocol: `EpochRotate.MemberSig`, `EpochKey`/`SyncEpochKey` gain `generator`/`member_hash`/`member_sig` (kept in sync with sshkey-term). **Tests:** `epoch_attestation_test.go` (attestation stored atomically + forwarded verbatim on the distributed `epoch_key`); existing epoch/rotation/failing-store + full integration suites green. Spec corrected: `PROTOCOL.md`, `PROJECT.md` (previously described an unsigned, unimplemented mechanism). Cross-repo design: sshkey-term `docs/planning/open/f7-room-member-attestation.md`.
- **Proactive new-device notification — shadow-device transparency Tier 1 (2026-05-31).** A new device registering under a user's identity was silently recorded (`UpsertDevice`, `ON CONFLICT DO NOTHING`) and only discoverable by manually opening the device list — so a stolen-key device on a fresh `device_id` could operate unseen (the Telegram-class shadow-device weakness). `UpsertDevice` now reports whether the row was a genuine first-seen insert (via `RowsAffected`), and on a new device the server fan-outs a `device_added{device_id, created_at}` to the user's **other** connected sessions only (never the new device, never other users) via the new `notifyNewDevice`. New `protocol.DeviceAdded`. The companion sshkey-term client surfaces it as a non-fatal alert (live push + a connect-time reconcile of the authoritative `device_list` against a locally-remembered set, which also catches a device added while the user was offline). This does **not** close masquerade of an *existing* `device_id` (an insider who saw your `device_id` in message payloads, or a full config clone) — `device_id` remains a self-asserted, unauthenticated label; closing that needs Tier 2 (per-device identity keys). Full finding + plan: `docs/planning/open/device-identity-transparency.md`. **Tests:** `device_added_test.go` (push to other sessions only; no-op without siblings), `store_test.go` (isNew true for first-seen, false for reconnect), and the integration harness's `readMessage` now skips the async `device_added` frame. Full server + integration suites green; vet + gofmt clean.
- **Reaction wrapped_keys validation + status_text bound + client host-key-algo pin; epoch-rotation membership enforcement; atomic last-admin guard (2026-05-30, crypto audit S7 + S8 + S9).** Round-2/3 hardening, all server-authoritative. **S7:** `handleReact` now validates a group/DM reaction's `wrapped_keys` against the current member set (exact-match-or-empty, mirroring send/edit) so a client can't attach entries for non-members — an empty map stays tolerated (a reaction reusing an existing key carries none; an empty/partial map is only self-inflicted undecryptability, never a leak), and the reaction `epoch` is deliberately **not** range-validated (reactions legitimately target past epochs); `set_status` now bounds `status_text` to 256 bytes (stored verbatim → storage-abuse vector; over-long silent-dropped + counted); and the **sshkey-term client** pins `HostKeyAlgorithms = [ssh-ed25519]` so a rogue/downgraded server can't negotiate a different host-key type (the server needs none — single Ed25519 host key). `avatar_id` is left shape-only — inert for file theft because downloads independently gate on the `file_contexts` binding. **S8:** `handleEpochRotate` now requires the client's `wrapped_keys` to **exactly** match the current room members (previously it only checked they *covered* the members, so an extra entry for a removed/stale member slipped through) **and** re-checks live `IsRoomMemberByID` in the per-recipient distribution loop — so a member removed between the `epoch_trigger` and the rotate reply (or in the TOCTOU window after the server's member read) is neither persisted nor sent the new epoch key. **S9:** the group last-admin invariant was a non-atomic check-then-act (`CountGroupAdmins` → demote/remove) that two concurrent admin actions could race to a **zero-admin group**; a new process-wide `groupAdminMu` serializes the check+mutate across the demote / remove / leave / delete / retirement-succession paths (acquired *after* the self-kick in `handleRemoveFromGroup` to avoid a re-entrant deadlock with `handleLeaveGroup`). Group admin state is mutated only in-process — `sshkey-ctl` cannot send protocol messages — so one mutex suffices (no DB-level conditional needed). **Tests:** `react_validation_test.go` (group/DM mismatch rejected, empty tolerated), `set_status_test.go` (over-long rejected, at-cap accepted), `epoch_exact_member_test.go` (extra non-member key rejected), `group_admin_s9_test.go` (concurrent demote never reaches zero admins, clean under `-race`); client `ssh_config_test.go` (Ed25519 host-key pin). Full server + protocol suites green; vet + gofmt clean. Audit: `docs/security/crypto_audit.md` (S7, S8, S9).
- **Read-receipt membership gate + upload byte-commit owner binding (2026-05-30, crypto audit S5 + S6).** Two server-side authorization gaps found in the round-2 crypto re-audit, both now closed. **S5:** `handleRead` wrote a read position and broadcast a `read` receipt with **no membership check** — unlike the adjacent `handleTyping`, which gates on exactly-one-context + `IsRoomMemberByID`/`IsGroupMember`/DM-party. A non-member could therefore write `read_positions` rows for arbitrary contexts and inject a (correctly self-stamped) read receipt into the real members' streams of a room/group/DM it didn't belong to — metadata only, no content leak. `handleRead` now mirrors the typing gate before `SetReadPosition`/broadcast; it deliberately does **not** reject retired rooms, since reading (hence marking read) stays valid in a read-only room. **S6:** `handleBinaryChannel` (Channel 3 upload byte-commit) looked up the pending upload by `uploadID` alone and never bound it to the authenticated channel user, so a user who learned another's in-flight `uploadID` (a 126-bit `crypto/rand` nanoid) could write the bytes on their own channel. It now rejects when `pending.user != userID`, tearing down the offending channel **without** `failUpload` (the victim's pending upload must survive — otherwise the check would itself be a cross-user DoS) and **without** draining the attacker-declared size. Both are LOW severity (metadata-only / high-entropy precondition); neither touches E2E content. **Tests:** new `read_authz_test.go` (non-member room/group/DM silent-drop + signal, empty/ambiguous malformed, member writes-position-and-relays-to-other-sessions-only, retired-room-allowed) and `upload_owner_test.go` (cross-user commit rejected + victim's pending upload intact). Full server suite green; vet + gofmt clean. Audit: `docs/security/crypto_audit.md` (S5, S6).
- **SSH transport algorithm allowlist pinned; actor-authority invariant locked by test (2026-05-30, crypto audit S4 + S1).** The `ssh.ServerConfig` set no `Ciphers`/`MACs`/`KeyExchanges`, inheriting `golang.org/x/crypto/ssh` v0.49.0 defaults — modern, but still permitting the non-AEAD `aes*-ctr` ciphers and only *offering* (not requiring) the post-quantum KEX. New `secureSSHConfig()` (server.go), wired into `New()`, pins an explicit allowlist: **Ciphers** AEAD-only (`chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com`, `aes128-gcm@openssh.com`); **KeyExchanges** ML-KEM-768 + X25519 post-quantum hybrid (`mlkem768x25519-sha256`) preferred with a classical `curve25519-sha256` fallback; **MACs** ETM-SHA2 (`hmac-sha2-{256,512}-etm@openssh.com`, unused under AEAD but pinned). The PQ hybrid gives the SSH transport harvest-now-decrypt-later resistance for **routing metadata only** — E2E message content is unaffected (sealed separately by the client's classical X25519 ECIES wrap). A network MITM cannot force the classical fallback: the KEXINIT algorithm lists are bound into the signed exchange hash, so a downgrade breaks the handshake. Strict-KEX (Terrapin / CVE-2023-48795) remains auto-applied. Pinned explicitly so a future x/crypto default change can't silently weaken the suite; the sshkey-term client pins the identical set and both ends run the same x/crypto, so the negotiated KEX is always the hybrid (no compatibility risk; pre-launch). **S1 (no behavior change — by design):** the audit confirmed the server is already *actor-authoritative* — it stamps `from`/`deleted_by`/`pinned_by`/reaction `user` from the authenticated session and the inbound frames carry no actor field — so server-side signature verification was deliberately NOT added (it is redundant against a malicious client and useless against a malicious server; the real authenticity fix is client-side). Instead a reflection regression test (`actor_authority_test.go`) locks the invariant: it fails if any inbound frame (`Send`/`SendGroup`/`SendDM`/`Edit{,Group,DM}`/`Delete`/`React`/`Unreact`/`Pin`/`Unpin`) ever gains a client-settable actor field. **Tests:** `internal/server` — algorithm policy contract (mlkem-first, AEAD-only, no weak primitive), `New()` wires the pin, and a TCP-loopback handshake proving the pinned suite interoperates AND rejects a weak-only (`aes128-cbc`) client at cipher negotiation; plus the actor-authority guard. Full server + protocol suites green; vet + gofmt clean. Audit: `docs/security/crypto_audit.md` (S4 fixed, S1 guarded).

### Added
- **`server_order` — server-authoritative per-conversation message commit order (2026-05-28, server-side foundation / S1).** Foundation for deterministic client scroll-back ordering: the server now assigns a monotonic, per-conversation `server_order` to every stored message and emits it on the wire so clients can page and sort by the server's committed order rather than guessing from local `rowid` or `(ts, id)` (which drift after out-of-order history backfill and cannot disambiguate same-second messages). **Schema:** the per-conversation `messages` table (shared by rooms, groups, and 1:1 DMs via `initMessageDB`) now uses `server_order INTEGER PRIMARY KEY AUTOINCREMENT` with `id TEXT NOT NULL UNIQUE` — so `server_order` is the rowid alias (existing `ORDER BY rowid` queries already order by commit order) and AUTOINCREMENT keeps it monotonic and never-reused. Each conversation DB has its own counter, so `server_order` is per-conversation, not global. Clean schema, no compat migration (pre-launch). **Store:** `StoredMessage.ServerOrder`; `insertMessage` and `Insert{Room,Group,DM}Message` now return the committed `server_order` (`LastInsertId` on the same Exec — bound to the insert, not a loose later lookup); every message scan (`scanMessages`, used by all load/since/before queries across room/group/DM) reads it. **Wire:** `ServerOrder int64 \`json:"server_order,omitempty"\`` added to the `message`, `group_message`, `dm`, and `deleted` envelopes; the send handlers patch the committed order onto the live broadcast (ID and TS are app-generated and stored as-is, so `server_order` is the only DB-assigned field — no drift); sync and history emission (`storedToRawMessages` / `storedToRawDMMessages`) carry it; soft-delete keeps the row, so tombstones preserve the original `server_order`. **Additive + non-breaking:** `omitempty`, and existing clients ignore the new field — the term client does not consume `server_order` until the companion term-side slice (S2: per-conversation term schema + persistence) lands. **Tests:** `internal/store` (monotonic per-conversation assignment, read-back, tombstone-preserve) and `internal/server` (sync/history emission carries `server_order` on room/group/DM message + room/DM tombstone). Full server suite green; vet + gofmt clean. `PROTOCOL.md` documents the field. Design record: gitignored `history-state-model.md` step 8 / S1.

- **Unknown-key storm bounding for `pending_keys` — TTL + hard row cap + notify rate-limit (2026-05-25).** An unauthenticated attacker can open many SSH connections with fresh random Ed25519 keys; each new fingerprint sails past the per-fingerprint block list and (after the per-IP `failed_auth_per_minute` limit) lands a new `pending_keys` row plus a first-attempt `admin_notify`. The per-IP limit already bounds a single source; this bounds the **distributed** case and **total growth** without ever denying admission (an unknown key gets no session regardless — this only bounds the cost of *recording* the storm). **Storage (gaps A/B):** new `store.PruneOldPendingKeys(maxAgeSec)` ages rows out by **`first_seen`** (first contact, NOT `last_seen` — so a key that keeps reconnecting can't keep its row alive past the TTL; the cutoff is an in-query SQLite `datetime('now', ...)` TEXT comparison, matching the schema's TEXT timestamps rather than the Unix-int shape `PruneOldRoomDeletions` uses), and `store.EnforcePendingKeyCap(maxRows)` evicts the least-recently-active rows (`ORDER BY last_seen, first_seen, rowid, fingerprint` — `rowid` is the insertion-order tie-breaker for the many storm rows sharing a second-resolution timestamp; portable `rowid IN (SELECT … LIMIT ?)` deletion). Two new indexes (`pending_keys(first_seen)` for the TTL, `pending_keys(last_seen, first_seen)` for list/cap). The prune+cap runs once at startup (log-and-continue, like `pruneOldQuotaRows`) and seeds the prune interval so the first unknown key after startup does not repeat the same maintenance pass. On the unknown-key path, `logPendingKey` enforces the hard row cap immediately after recording the current key (so a fresh first-contact never leaves the table at `max_rows+1`), while the heavier TTL prune remains single-flight and interval-gated through `maybePrunePendingKeys()` (claims the last-prune timestamp under a mutex before the lock-free DB work, so a storm triggers at most one full TTL prune per interval and never blocks the auth path). **Notify (gap D):** first-attempt `admin_notify` pushes now pass through a **dedicated** pending-key token bucket (`notify_burst` immediate, then ~`notify_per_minute` sustained) — deliberately NOT the shared auth limiter (which clamps burst to ≥5) and NOT inside the generic `notifyAdmins` dispatcher (so a pending-key storm can't suppress unrelated quota/admin notifications). The per-key DB row is recorded regardless; only the push is throttled. **Config:** new hot-reloadable `[server.pending_keys]` (`max_age_hours = 168`, `max_rows = 1000`, `prune_interval_seconds = 60`, `notify_per_minute = 5`, `notify_burst = 1`); `ServerConfig.Validate` requires all positive and `1 <= notify_burst <= notify_per_minute`; copied in `reloadServerConfig` alongside `AutoRevoke`/`Quotas`. **Tests:** `internal/store` (TTL ages by `first_seen` incl. a reconnecting key still aging out; cap evicts oldest-by-`last_seen` + same-second `rowid` tie-break + no-op under cap); `internal/config` (defaults, require-positive + burst-bound validation, omitted-section-keeps-defaults regression); `internal/server` (limiter burst/refill, `logPendingKey` storm throttles notifications to `notify_burst` while recording every row, immediate cap wiring, startup interval seeding, and the `maybePrune` interval single-flight guard). Docs: `default_server.toml` + `docker/config/server.toml` annotated `[server.pending_keys]` block; README/PROJECT hot-reload lists; `PROTOCOL.md` notes `pending_key` `admin_notify` is best-effort/rate-limited with `pending_keys_list` as the authoritative operator view. Design record: gitignored `unknown-key-storm-hardening.md`.

- **`room_update` client request handler — in-session topic updates for server admins (2026-05-12).** Closes the long-standing silent-drop bug where `sshkey-term` clients sent `room_update` envelopes (via `handleTopicCommand` + `SendRoomUpdate`) but the server dispatcher had no matching case, so the requests went nowhere and the only feedback path was the client's optimistic "Topic update sent — pending server confirmation" status-bar message. Server-side spec: `topic.md` in this repo.

  Wire shape (`protocol.RoomUpdate`): `{type:"room_update", room:"rm_...", topic:"...", corr_id:"corr_..."}`. Scope is intentionally topic-only — room renames stay operator-only via `sshkey-ctl rename-room`. Empty `topic` clears the topic.

  Authorization is **server-admin** (`users.admin` flag — set via `sshkey-ctl approve --admin` / `sshkey-ctl promote`) AND **current room member**. Rooms have no per-room admin role in this phase; the membership requirement restricts in-session topic moderation to admins who are also participants of the affected room. The CLI path (`sshkey-ctl update-topic`) continues to bypass the membership check for operator-override scenarios.

  Handler flow (`handleRoomUpdate` in new `internal/server/room_update.go`, 12 steps): decode → corr_id validate → store nil-guard → rate limit (BEFORE auth, so unauthorized spam is bucket-bounded against DB-read DoS) → server-admin → room membership → load row → retired check → idempotency → `SetRoomTopic` → shared post-write side-effects → no direct success frame (caller receives `room_updated` via fan-out).

  **Same-value topic** is accepted as a successful no-op: the caller receives a `room_updated` echo for UI confirmation, but no DB write, audit row, `room_event` insert, or fanout to other members. Symmetric with the CLI path which silently writes the same value.

  **Errors** (all post-unmarshal errors echo `corr_id` for send-queue correlation parity with the other corr_id-carrying verbs): `forbidden` (non-admin), `rate_limited` with `retry_after_ms` (`room_admin_action:<user>:<room>` bucket — distinct prefix from `group_admin:` so grep + audit-log review unambiguously identifies which path produced a signal), `unknown_room` (non-member OR room doesn't exist — privacy parity), `room_retired`, `invalid_message` (malformed frame; pre-unmarshal, carries empty corr_id). ## [v0.3.0] - 2026-05-12

### Removed
- **`sshkey-ctl bootstrap-admin` command + server-side admin keygen path entirely (2026-05-09).** The command and its supporting code (`cmd/sshkey-ctl/bootstrap_admin.go`, `bootstrap_admin_test.go`, ~880 lines together) generated an Ed25519 keypair on the server, encrypted the private key with an interactively-prompted passphrase, wrote it to disk, and instructed the operator to `scp` it off and `shred -u` the original. **The model itself was wrong for a key-as-identity protocol.** Server-side keygen meant the operator briefly held the new admin's private key — even encrypted — and the cleanup relied on `shred`, which is not reliably destructive on APFS / SSDs with wear-leveling / Docker overlay layers. A compromised server during the window between keygen and shred would yield the admin's private key. The whole point of the rest of the system (key-as-identity, no rotation, fingerprint-pinned profiles) is that private keys never leave the user's machine — bootstrap-admin inverted that property and patched it with a workflow assumption.

The new `--admin` flag (see Added below) makes it one command instead of two; the disaster-recovery case is structurally identical (the new admin's public key arrives via any out-of-band channel — email, Signal, hand-delivery — and approve handles it). ### Added
- **`sshkey-ctl approve --admin` flag (2026-05-09).** Flips the new user's admin flag in the same approve transaction that inserts the user row. Equivalent to `approve` + `promote <user_id>` but in one command, and atomic — no observable mid-state where the user exists as a non-admin. Primary use case is the first-admin bootstrap (post-bootstrap-admin removal): the fresh-server "users.db is empty" log warning explicitly points at this path. `promote` and `demote` remain the post-approval verbs for changing admin status of existing users.

- **`sshkey-ctl purge-pending` and `sshkey-ctl reject-pending` commands (2026-05-09)** for clearing pending-key entries from both the `pending_keys` SQLite table AND `pending-keys.log`. Two distinct verbs covering the two real admin needs:
  - `purge-pending --fp FP` clears a single pending key from DB and log; the user can retry on next connect and will land back in the queue. `purge-pending --all [--yes]` clears the entire queue wholesale; `--yes` skips the confirmation prompt (without it, prints the count and the re-run hint without doing anything destructive).
  - `reject-pending --fp FP [--reason TEXT]` clears the pending key from DB and log AND adds its fingerprint to the block list (`blocked_fingerprints` table — the same primitive `block-fingerprint` uses, checked at the SSH handshake layer BEFORE writing to `pending_keys`). The user is prevented from re-entering the queue. Inherits the approved-user warning from `block-fingerprint` so an operator can't accidentally block a user who's already approved (the warning suggests `retire-user` instead).

  Both commands route DB+log clearing through the existing `clearPendingKeyState` helper that the `approve` flow already uses, so the three "remove a pending key" code paths are now unified — same behavior, same atomic write semantics on the log file.

  Replaces the previous `reject` command (clean removal, no soft-deprecation alias — pre-launch state, no users to break). The old `reject` was bug-shaped: it only pruned matching lines from `pending-keys.log` and did NOT delete the corresponding row from `pending_keys`, so an admin "rejecting" a key would see it disappear from `sshkey-ctl pending` (which reads the log) but the DB row would persist, allowing accidental dual-state. Audit-log entries (`purge-pending`, `purge-pending-all`, `reject-pending`) record each verb invocation with the fingerprint and reason.

  **10 new tests** in `cmd/sshkey-ctl/main_test.go` covering the per-key DB+log clear, the `--all` confirmation gate (no destructive action without `--yes`), wholesale clear correctness, conflicting-flag rejection (`--fp` and `--all` mutually exclusive), `reject-pending`'s blocklist-add side effect, idempotence when re-rejecting an already-blocked fingerprint, the SHA256-prefix validation, and the missing-flag error paths.

- **Phase 21 F6 — lockfile TOCTOU race closed via tmpfile+Link (2026-04-19).** Pre-fix, `lockfile.Read()` checked if the existing lockfile's PID was alive and on stale/absent the caller proceeded to `lockfile.Write()` (Read-then-temp-write-then-Rename). Two `Server.New` calls racing could both pass the aliveness check in the microsecond window between reads, then both rename; the second clobbered the first's lockfile with both processes continuing to run. Severity reassessment 2026-04-19 downgraded this to LOW (realistic scenarios require deliberate operator misconfig; SQLite MVCC prevents corruption; worst case is brief split-brain until ops notices) — but upgraded to fix-now because the primitive swap was cheap. New implementation: stage the complete PID+timestamp payload in a per-process `.sshkey-lockfile-*.tmp` file in the same directory as the target, then call `os.Link(tmpName, path)` — POSIX link(2) is atomic and returns EEXIST if the target exists, making it the canonical exclusive-create primitive for file-based locks. Because the tempfile holds the complete payload before Link, readers always see complete content on the linked path; there is no empty-file or partial-content race that a naive `O_EXCL`-on-final-path approach would expose (we hit that in the first refactor attempt and caught it via the new concurrent test). Stale-recovery retries Link once after removing the stale file; concurrent stale-recovery collisions return `ErrAlreadyRunning` against the winning PID rather than looping. `defer os.Remove(tmpName)` cleans the staging file whether Link succeeded (inode persists via the linked path) or failed. New drift-guard test `TestWrite_ConcurrentAcquisitionExactlyOneSucceeds` runs 20 goroutines racing to acquire the same lockfile, deterministically asserts exactly one success and 19 ErrAlreadyRunning — pre-fix this would have been flaky or silently wrong; post-fix it's locked in by the atomic link(2) primitive. All 16 lockfile tests green; `go build ./... && go vet ./... && staticcheck ./...` clean; full `-race` suite green. See `docs/security/audit_v0.2.0.md#F6`.

Only the user's most recent non-deleted message in the current context is editable; non-members, non-authors, and deleted-row failure modes all collapse into byte-identical `ErrUnknownX` responses (privacy invariant). Authorship is surfaced via `ErrEditNotMostRecent`; room edits must be in the current-or-previous epoch grace window or they get `ErrEditWindowExpired`. Reactions on edited messages are cleared in the same transaction as the payload replace — clients unconditionally drop local reaction state for the edited message ID on receipt of the `edited` event (no per-reaction `reaction_removed` broadcasts). New rate limit bucket `EditsPerMinute` (default 10/min, shared across all three verbs per user). New store helpers `UpdateRoomMessageEdited` / `UpdateGroupMessageEditedWithKeys` / `UpdateDMMessageEditedWithKeys` / `GetRoomMessageByID` / `GetGroupMessageByID` / `GetDMMessageByID` / `GetUserMostRecentMessageID{Room,Group,DM}`. New `edited_at INTEGER NOT NULL DEFAULT 0` column on the per-context `messages` schema (single CREATE TABLE edit via `initMessageDB`, no ALTER per the no-live-users policy). Byte-identical privacy regression tests: `TestHandleEdit_PrivacyResponsesIdentical`, `TestHandleEditGroup_PrivacyResponsesIdentical`, `TestHandleEditDM_PrivacyResponsesIdentical`. Plus happy-path, most-recent rejection, epoch-window rejection, retired-room rejection, deleted-row collapse, and reaction-clearing tests. See `PROTOCOL.md` "Message Editing" section for the wire format and `message_editing.md` for the design write-up.
